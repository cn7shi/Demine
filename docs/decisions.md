# 工程决策记录

## ADR-001：先交付自动观察与回放（2026-10-05）

背景：Agent 的任务完成回复会省略执行摩擦。用户希望接入后自动知道发生过什么。

选择：M0/M1 自动发现指定项目下的 Codex 会话，增量采集并提供浏览器时间线。本阶段不调用模型、不生成因果解释。

原因：先证明来源可靠，再解释原因。接入失败、漏记录或重复展示，会让后续经验沉淀建立在不可靠材料上。

代价：首版呈现事实，不自动判断“值得学习的坑”。问题归组与用户经验属于 M2/M3。

## ADR-002：只读日志适配 + 单进程本地服务

选择：Rust + SQLite + 普通 TypeScript 前端。定期发现与读取本地记录；MCP、hooks 和 App Server 后续接入。

原因：现有本机会话已确认包含消息、调用、结果及标识符；轮询能自然补偿文件通知遗漏，也无需修改 Codex 配置。SQLite 使事件与读取进度原子提交。前端不需要框架状态管理即可完成当前三栏回放。

代价：有轮询延迟；日志格式不是稳定 API，必须隔离适配器并声明实测范围。扫描大型历史目录的效率需要持续评估。

参考：[Codex Hooks 格式限制](https://learn.chatgpt.com/docs/hooks)、[App Server](https://learn.chatgpt.com/docs/app-server)。

## ADR-003：证据、去重与可见性

选择：保存行级来源与偏移；时间线条目另外组织。已知重复表示按条目标识或对应关系归并。未知格式保留为未识别记录，坏行单独提示。隐藏推理、系统/开发者指令不导入正文。

原因：实际 Codex 会话同时包含 `response_item` 与 `event_msg/item_completed`。去重必须保留来源，不能仅按文本相同删除，因为相同命令可能真的执行多次。

代价：不能承诺恢复内部思考，也不把本地数据库称为整个 Codex 日志的完整备份。一次操作结束只表示执行状态。

## ADR-004：稳定事件序号与保守重读

选择：文件偏移、已提交前缀摘要、事件与原文在事务内保存。检测到截断或已读部分变化时开启新一代来源，保留上一代历史；不覆盖已有证据。

原因：同名文件可能被替换，仅比较长度不能识别同长度重写。完整前缀校验成本较高，但当前阶段优先准确性，后续用实际数据决定优化。

代价：每次变化需校验已提交前缀。大文件速度可能受影响；界面与文档须明确历史代次。

## ADR-005：无需前端工具链即可启动

选择：生成的 `web/public/app.js` 随源码提交，Rust 编译时内嵌静态资源。开发者编辑 TypeScript 后运行 `npm run build`，CI 检查生成文件一致性。

原因：用户只需编译/运行一个程序，不必在运行时启动前端开发服务器。

代价：仓库同时保留 TypeScript 与生成 JavaScript；禁止手工修改生成文件。

## ADR-006：保守处理重复表示与消息归属

选择：有一致 item/call ID 时合并请求与结果，保留每条来源。用户消息在两种表示中可能具有不同 ID，因此只在相同来源代次、同类消息相邻、原始行距离不超过四行、内容相同且显式回合不冲突时隐藏低优先级表示。用户原生表示必须出现在对应运输记录之后。没有对应表示的旧消息继续可见。

原因：直接按“整个会话已出现新格式”隐藏旧格式，会遗漏升级前的真实消息；仅凭文本去重也会吃掉重复尝试。新用户输入可能早于新回合开始事件，不能自动归入上一轮。

代价：异构表示只能做保守的展示归并，不能承诺所有版本都完全去重。原始证据保留，底层工具编排默认折叠。未来如获得稳定的关联 ID，将替换启发式消息归并。

## ADR-007：按修订游标更新界面

选择：时间线按事件 ID 排序，但增量读取按最后关联的原始记录 ID 推进。初始加载最近 100 条，按需加载更早记录。来源代次独立展示。

原因：一个调用在很久以后才收到结果；只按新增事件 ID 轮询会永远漏掉对旧条目的更新。前端保留已加载内容，断线时显示状态并继续尝试连接。

代价：搜索与类型筛选作用于已加载记录；尚未实现全库全文搜索。

## ADR-008：审查后的数据过滤与数据库迁移

背景：OCR 委托审查发现 `response_item/compaction` 含加密内部历史及附加内部元数据，原先被未知类型兜底规则复制进证据。

选择：此类型只保留压缩标记、时间与 ID；模式升级至 2，打开版本 1 数据库时在事务内用同一适配规则重新过滤受影响记录，保持来源进度和事件 ID 不变。

原因：只修改新记录的适配器不能处理已入库内容；删除整个数据库又会丢失用户历史。已知敏感内部类型必须先于未知格式兜底处理。

代价：旧版程序不能再写入新模式数据库；迁移修正逻辑记录，不承诺对磁盘空闲页、备份或历史 WAL 做安全擦除。仍不把来源日志当作通用敏感内容清洗器。

## ADR-009：历史分页与实时修订分别推进

背景：很早的调用收到结果时，事件 ID 仍旧，但修订号较新；将所有已加载事件的最小 ID 当成历史边界，会跳过中间尚未读取的记录。并发历史请求也可能晚于实时更新返回。

选择：用独立历史边界追踪连续加载的历史页；条目合并比较修订号，拒绝旧内容覆盖新内容。增量游标只前进。

原因：历史位置与内容新旧是两个维度，不能共用一个由界面集合推算的边界。

代价：增加少量界面状态；用浏览器响应乱序测试约束，而不依靠请求通常按顺序完成的假设。

## ADR-010：明确失败信号不能被成功返回掩盖

选择：原生操作明确标记 `failed` 时保留失败状态，即使没有退出码；`--once` 在报告存在扫描错误时保留 JSON 输出并返回非零退出码。

原因：命令启动失败可能根本没有退出码；脚本通常依赖进程退出状态判断接入是否成功。这些状态描述观测/采集是否成功，不替代工程问题是否解决的判断。

## ADR-011：历史目录缺失时仍解析已有祖先的路径别名

背景：首次云端 Windows 测试中，子目录尚不存在的第二个会话被漏采；Linux 同一测试通过。检查发现原实现只有整条路径存在时才规范化，否则直接使用原始文本，项目根与历史工作目录可能使用不同的路径表示。本地通过目录联接构造同类条件，已复现失败。

选择：从完整路径向上查找最深的可规范化祖先，解析其符号链接、目录联接或短名称，再拼回缺失的后缀并进行词法规范化；项目比较仍使用目录分隔符边界。

原因：已经删除的工作目录仍可能属于本项目。只在测试里创建那个目录，会掩盖真实的历史采集遗漏；直接比较未解析的前缀，还可能把实际指向其他项目的路径误归入当前项目。

代价：缺失多层目录时增加少量文件系统查询；无法恢复已经删除的链接过去指向哪里，仍以当前可访问的祖先为依据。新增回归同时覆盖缺失后缀、别名等价、父目录越界与跨项目排除；见 [测试记录](testing.md)。
