## 实际使用方式

使用本机 Alibaba OpenCodeReview **1.12.12（182898c）** 的 `delegate preview` 与 `delegate rule`。OCR 输出文件清单及匹配规则，本对话的编程助手执行代码审查、复现与修复。未配置 OCR 的模型 API，也未运行由 OCR 单独调用模型的 `ocr review`；审查执行者与实现者相同。

这一模式由 [项目官方说明](https://github.com/alibaba/open-code-review#quick-start) 支持。CLI 已有相应命令，无需为此次自查另装助手插件。

实际命令如下；本机进程的 PATH 尚未刷新，因此执行时使用了已安装 `ocr.cmd` 的完整路径：

```powershell
ocr delegate preview --format json --background-file AGENTS.md --exclude 'web/public/app.js,Cargo.lock,package-lock.json'
ocr delegate rule --format json --background-file AGENTS.md <preview 返回的文件路径列表>
```

初始清单共 29 个变更文件，OCR 选中 19 个：Rust 源码/集成测试、TypeScript、页面与样式、启动测试服务的脚本、构建配置和 CI。规则按 Rust、JS/TS、Cargo、npm、JSON、GitHub Actions、通用检查共 7 组输出。

主动排除锁文件和生成的 JavaScript；OCR 默认排除了 Markdown 与浏览器 spec，后者另行阅读并补测。文档作为产品契约核对；新增 CLI 和分页回归测试亦已检查。没有向额外模型服务发送仓库或真实会话。

工具原始输出及失败复现摘要保存在 Git 忽略目录 `target/ocr-review/`：`preview.json`、`rules.json`、`reviewed-files.txt`、`regression-before.txt`、`browser-before.txt`。下列发现是助手按规则核验的结论，不是规则导出命令自动生成的审查意见。

## 已确认并修复的发现

### R1 · P1：压缩内部字段绕过证据过滤

位置：`src/adapter.rs` 的 `response_item` 未知类型分支；修复涉及 `src/store.rs` 的数据库迁移。

触发：来源包含 `response_item/compaction`。实际样本的字段名包含 `encrypted_content` 和 `internal_chat_message_metadata_passthrough`；原先的默认分支复制整个原文，使这些字段可通过证据接口读取。这违背项目的内部内容过滤边界。核验只输出字段名，没有打印或尝试解读密文内容。

修复：只保存压缩标记的白名单字段；模式升级为 2，对旧库受影响记录使用同一规则重新过滤，在事务内保留历史、事件 ID 与读取进度。

验证：新增“新压缩记录过滤”和“版本 1 迁移不丢进度”两个测试，修复前均失败、修复后均通过。真实数据库迁移后模式为 2，保留 1 条压缩标记，含上述禁止字段的压缩记录数为 0。此处确认逻辑数据库内容，不声称已安全擦除磁盘历史页或备份。

### R2 · P2：迟到结果使历史分页跨过未读记录

位置：`web/src/app.ts` 加载更早记录时的边界计算。

触发：初始加载到事件 200，随后收到事件 50 的迟到结果。原实现从界面所有条目的最小 ID 算历史边界，下一页变为 `before=50`，事件 51–199 因而被跳过。

修复：独立保存连续历史页的边界，只有加载历史页能推进它；增量修订不能改变该边界。

验证：浏览器回归用例修复前实际请求 50，修复后请求 200，能够加载中间的事件 100。

### R3 · P2：乱序历史响应覆盖最新执行结果

位置：`web/src/app.ts` 的 `merge`。

触发：历史请求取得“进行中”的旧条目但延后返回；实时刷新先取得“已收到返回”的新修订。旧响应随后无条件覆盖新状态，而增量游标已经前进，可能长期停在旧状态。

修复：合并时比较修订号，保留较新的条目；增量游标只前进。

验证：浏览器测试控制两个响应的到达顺序。修复前状态退回“进行中”；修复后始终保留“已收到返回”。

### R4 · P2：没有退出码的明确失败被显示为执行结束

位置：`src/adapter.rs` 原生命令与文件操作状态适配。

触发：命令无法启动或文件改动失败，记录明确带 `status=failed`，但没有退出码。原实现只通过命令退出码或 MCP 专门分支判断失败，普通命令/文件事件会落到通用完成状态，遗漏失败计数与筛选。

修复：对已识别的原生操作保留明确失败信号，不要求必须有退出码。

验证：同时构造命令启动失败和文件改动失败；修复前失败计数为 0，修复后为 2。

### R5 · P2：单次扫描失败仍返回成功退出码

位置：`src/main.rs` 的 `--once` 分支。

触发：目录里有无法识别会话头的文件。报告虽然含错误，进程仍成功退出，脚本或接入检测可能将其误判为成功。

修复：仍输出可解析 JSON，但报告含扫描错误时返回非零退出码。普通待识别事件属于已保存证据，与来源无法读取的扫描错误分开处理。

验证：使用真实可执行文件运行命令行测试；坏头文件存在时失败退出，移除该测试文件后成功退出。修复前此测试失败。
